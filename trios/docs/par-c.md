# File Boundaries

1. Each source file in the Trios project owns a single, well-defined responsibility. A file should encapsulate one architectural concern — one model, one transport, one parser, or one view — so that a developer can reason about its contents without needing to open unrelated files. When a file begins to serve two masters, it is a signal that extraction is overdue: split the file along the seam where the two concerns diverge, and let each half stand on its own with a clear name and a focused import surface.

2. Files communicate with each other through explicit, narrow interfaces rather than through shared mutable state or implicit coupling. The Onion (Ring) architecture enforces this by declaring dependencies as protocols in the core layer and providing concrete implementations in infrastructure. A file in the presentation layer may depend on application-layer protocols, but it must never reach across to infrastructure directly. This unidirectional flow keeps file boundaries meaningful: each boundary is a contract, not a suggestion, and violating it produces a compile-time error rather than a runtime surprise.

3. The practical test for whether two pieces of code belong in the same file is the co-change principle. If every change to piece A is accompanied by a change to piece B, they likely belong together; if they change independently, they should live in separate files even if they seem conceptually related. Applying this test consistently produces a codebase where the cost of finding the right file is low, the cost of understanding a single file is bounded, and the blast radius of any given edit is predictable. File boundaries are not just organisational — they are the primary unit of cognitive load management for every developer who touches the project.
