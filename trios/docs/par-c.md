1. Every layer in the Trios architecture owns a distinct set of Swift files, and those boundaries must remain explicit. The Core layer (`ChatMessage.swift`, `ChatEvents.swift`, `ChatProtocols.swift`) defines data models and protocols with zero external dependencies. Infrastructure (`SSETransport.swift`, `HealthCheckTransport.swift`, `UIMessageStreamParser.swift`, `ConversationPersister.swift`) implements those protocols against concrete frameworks like `URLSession` and `UserDefaults`. No Infrastructure file may export types that belong to Core, and no Core file may import an Infrastructure module — the dependency arrow points inward, always.

2. The Application layer (`ChatViewModel.swift`, `ConversationStateMachine.swift`, `EventThrottler.swift`) sits above Infrastructure and orchestrates real-world concerns: streaming state transitions, SSE throttling at roughly 30 FPS, and message-list mutations. It depends on both Core types and Infrastructure abstractions but never reaches into Presentation. When a new cross-cutting concern appears — caching, logging, analytics — it belongs here or in a dedicated service file within this layer, not bolted onto a Core model or a SwiftUI view.

3. The Presentation layer (`ChatPanelView.swift`, `MessageBubbleView.swift`, `TypingIndicatorView.swift`, `ToolCallCardView.swift`, `GlassmorphismBackground.swift`) renders nothing but state it receives from the Application layer. Views must not instantiate transport objects, persist data, or parse SSE events; they observe `@Published` properties and dispatch user intents back through the view-model. Keeping these file boundaries clean is what makes the ring testable, replaceable, and safe to refactor — a view that imports `SSETransport` is a bug, not a shortcut.
