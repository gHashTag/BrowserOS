# File Boundaries (Branch C)

1. A file boundary is the line where one source file's responsibilities end and another's begin. In a well-structured project, each file owns a single, cohesive concern — a data model, a protocol, a view, or a layer of infrastructure. When a file accumulates unrelated logic, the boundary has blurred, and every consumer of that file pays the cost in confusion, longer build times, and harder review. Clear boundaries make files easy to locate, easy to test in isolation, and safe to modify without ripple effects across the codebase.

2. The Trios project enforces file boundaries through its Onion (Ring) architecture. The Core layer defines types and protocols with zero external dependencies. Infrastructure builds on Core to provide concrete transports and parsers. Application wires Infrastructure together into state-managed view models. Presentation renders that state with SwiftUI views. A file in the Presentation layer must never import a concrete transport; a file in Infrastructure must never reference a SwiftUI view. These rules are not stylistic preferences — they are compile-time guarantees that keep the dependency graph pointing inward and prevent the circular dependencies that collapse layered architectures.

3. Maintaining boundaries is an ongoing discipline, not a one-time design decision. Every pull request, every new feature, and every refactor is an opportunity to either reinforce or erode them. The Queen's review process checks boundary violations before code lands: if a worker adds a UIKit import to a Core file, or reaches across layers to call a view model from a transport, the review flags it and the worker must restructure. File boundaries that are defended consistently let the team scale — new contributors can reason about a single file without understanding the entire system, and changes stay local instead of cascading into unrelated modules.
