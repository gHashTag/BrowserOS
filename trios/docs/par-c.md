# File Boundaries

1. A file boundary defines which files a worker may create or edit. The Queen specifies an allow-list of paths in the spec header under a `Boundary` section, and every edit outside those paths is silently dropped — not reviewed, not merged, not argued about. This hard constraint prevents merge conflicts between parallel workers, keeps reviews focused on a single coherent change, and makes it trivial to verify that a branch stayed within its lane.

2. File boundaries are not suggestions or best-effort hints; they are enforced at the infrastructure level. When a worker writes to a path outside its declared boundary, that write never reaches the shared checkout. The Queen reviews only what falls inside the boundary, which means a worker can safely experiment with scaffolding, scratch files, or throwaway scripts elsewhere without polluting the review surface or risking an accidental merge of unintended changes.

3. The most common boundary-related failure mode is hidden coupling: two tasks that appear independent because they touch different files, but in reality depend on the same interface, type, or shared module. The spec header is designed to surface these early — workers who notice that their boundary overlaps logically with another task should raise the concern rather than silently expanding their scope. Unstated scope creep is where parallel reviews turn into arguments, and explicit boundaries are the tool that prevents it.
