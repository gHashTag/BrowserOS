# File Boundaries — Layer Separation

1. Every Swift source file in the Trios project belongs to exactly one ring layer: Core, Infrastructure, Application, or Presentation. A file may import types from the same layer or an inner layer, but never from an outer one. This means Presentation code can depend on Application, Infrastructure, and Core; Application depends on Infrastructure and Core; Infrastructure depends only on Core; and Core depends on nothing within the project itself. When a file is moved or created, its layer membership must be recorded in the architecture map and the import graph must remain acyclic.

2. Public protocols live in the Core layer (`ChatProtocols.swift`), while concrete implementations live in the layer that owns their concern. For example, `SSETransport.swift` (Infrastructure) implements `ChatTransportProtocol` (Core), and `ChatViewModel.swift` (Application) consumes both without knowing the concrete type. Never place a protocol and its only implementation in the same file unless they are both Core types; the boundary between abstraction and implementation is what makes the ring testable in isolation and replaceable at the seam.

3. Test files mirror the layer structure of production code: unit tests for Core types must not import Presentation or Application modules, and snapshot tests for SwiftUI views may import Presentation but should not reach into Infrastructure directly. Shared fixtures and helpers live in a dedicated `TestSupport` directory that every test target can reference. When a test needs to cross a layer boundary to access an internal type, prefer adding a `@testable import` for the minimal layer rather than re-exporting internals through a higher layer.
