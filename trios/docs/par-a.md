# Parallel Work (Branch A)

1. Parallel work in the Trios project means assigning independent tasks to separate workers, each on its own branch, so that progress happens concurrently instead of sequentially. The Queen distributes slices of a larger goal, defines acceptance criteria for each slice, and merges the results. Workers never touch each other's branches; they own their checkout and are responsible only for the files listed in their specification. This isolation is what makes parallelism safe — no worker can accidentally clobber another's work because no two workers share a file boundary.

2. The precondition for parallel work is genuine independence. Two tasks are parallelizable only when their file boundaries do not overlap and neither depends on the other's output. When tasks share a file or an interface, they are serialized by nature: one must land before the other can build on top of it. The Queen detects hidden coupling during planning and either reassigns boundaries or resequences the work into a dependency chain. Trying to parallelize coupled tasks anyway produces merge conflicts, review thrash, and wasted effort — the very problems the model is designed to eliminate.

3. Coordination is centralized and explicit. Workers do not talk to each other; they communicate through the specification they receive and the branch they write to. The Queen tracks which branches are in flight, which have landed, and which are blocked. If a worker discovers scope that was not listed in the specification — something that seems obviously needed but was not requested — the correct action is to raise it, not to do it quietly. Unstated scope is where parallel work breaks down: one worker's silent expansion can collide with another worker's planned slice, turning an independent pair into a conflict pair.
