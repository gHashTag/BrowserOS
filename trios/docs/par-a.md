# Parallel Work (Branch A)

1. Parallel work means splitting a task into independent pieces that progress at the same time, rather than one after another. In the Trios project the Queen decomposes a large specification into worker-sized slices, each with its own acceptance criteria and file boundary. As long as two workers never touch the same file, they can run concurrently without coordination overhead. The wall-clock gain is real: three independent slices that would take six hours sequentially can finish in roughly two.

2. The branch is the unit of isolation. Each worker receives a dedicated Git branch (for example `queen/1147-write-docs-par-a-md-three-numbered`) and is told exactly which paths it may create or edit. No worker checks out another worker's branch, commits to it, or switches away from its own. The Queen owns the merge: it collects finished branches, reviews them against acceptance criteria, and lands only those that pass. Workers never merge their own work and never see each other's edits until the Queen integrates them.

3. Independence is the precondition that makes parallelism safe. When two tasks share a file or an interface they are no longer parallel — they are serialised with extra coordination cost. The specification therefore names every path a worker may touch and nothing else; anything outside that list is out of scope and must be raised, not done quietly. Hidden coupling is the enemy: the most expensive failures happen when two branches look independent but collide at merge time because both changed the same line or the same contract.
