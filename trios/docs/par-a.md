# Parallel Work — Branch A

1. Parallel work in the Trios project is organised by the Queen, who splits a large task into independent slices and assigns each slice to a dedicated branch. Each worker receives a specification with explicit acceptance criteria and a strict file boundary — the worker may touch only the paths listed in the spec and nothing else. This isolation prevents merge conflicts, keeps reviews focused, and lets the Queen attribute every edit to the correct branch without ambiguity.

2. The speedup from parallel work depends on how truly independent the slices are. When two workers edit disjoint files and depend on no shared intermediate output, the work is genuinely parallel and total wall-clock time shrinks proportionally. When slices share a file, an interface, or an implicit contract, the Queen must either serialise them or accept coordination overhead that erodes the benefit. The Queen's job is to detect these couplings at planning time, not at merge time.

3. Workers operate autonomously within their boundary: they read the spec, implement the criteria, and verify each one before stopping. They do not check out the branch, create it, commit, or switch context — the shared checkout stays clean for the user, the build, and every other worker. When the worker is done, the Queen reviews the diff against the acceptance criteria, and only then does the change land. This separation between doing the work and landing the work is what makes parallel branches safe.
