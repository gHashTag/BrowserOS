# Parallel Work

1. Parallel work in software development means multiple people or automated agents are actively working on different tasks at the same time, without blocking one another. The core idea is to split a large body of work into smaller, independent units that can proceed concurrently. This requires clear interfaces between the units so that each worker can make progress without needing to wait for the others to finish. When done well, parallel work dramatically reduces the wall-clock time needed to ship a feature or fix, because the slowest single task — not the sum of all tasks — becomes the bottleneck.

2. Effective parallel work depends on strong boundaries. Each unit of work must have a well-defined scope, a set of acceptance criteria, and an explicit list of what is out of scope. Without these guardrails, workers will overlap, produce conflicting changes, or silently expand into territory owned by someone else. The boundary document — whether it is a specification, a design doc, or a simple checklist — serves as the contract between parallel workers. It lets each person reason about what the finished state should look like without needing to coordinate every detail in real time.

3. Verification is what turns parallel work from chaos into a reliable pipeline. Every parallel unit must be independently verifiable: there must be a way to check whether that specific unit's criteria are met without depending on the completion of other units. This is why acceptance criteria are written before work begins, not after. When each worker can self-assess against the criteria and report a clear "met" or "not met," the integrator — whether human or automated — can merge results with confidence. Without this discipline, parallel work produces a pile of changes that nobody can confidently assemble.
