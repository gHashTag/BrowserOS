# Parallel Work — Paragraph Set A

1. Parallel work in a codebase begins with clear ownership boundaries. Each worker must know exactly which files, functions, or modules fall under their responsibility and which are shared. Without explicit boundaries, parallelism collapses into merge conflicts, duplicated effort, and silent crosstalk that only surfaces during review. The cost of drawing these lines up front is small; the cost of discovering them too late is measured in lost hours and frayed trust between collaborators.

2. The second pillar of effective parallelism is a shared verification strategy. When multiple agents work simultaneously, the definition of "done" must be unambiguous and mechanically checkable — acceptance criteria that can be tested without human interpretation. If one worker treats a passing build as sufficient while another expects full test coverage and documentation, the integration phase becomes a negotiation rather than a merge. A single, agreed-upon verification protocol keeps every worker honest and every deliverable comparable.

3. Finally, parallel work demands disciplined communication about scope. The temptation to fix something "obviously needed" while inside a file is the most common source of scope creep and review friction. Every worker should treat unstated work as a signal to raise a question, not an invitation to act silently. The best parallel teams enforce this through tooling — branch boundaries that drop out-of-scope edits, review checklists that map directly to acceptance criteria, and a culture where raising an issue is faster and cheaper than doing the wrong thing.
